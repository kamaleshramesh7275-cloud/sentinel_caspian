### 1️⃣ Problem Statement

In modern cloud-native environments, site reliability engineering (SRE) and DevOps teams face an overwhelming influx of real-time telemetry, stack traces, and automated notifications generated by APM (Application Performance Monitoring) tools like Sentry, Datadog, Prometheus, and CloudWatch. This current paradigm suffers from four critical bottlenecks:

1. **Severe Alert Fatigue & Noise Pollution**: 
   High-frequency system exceptions produce duplicate alert storms. Single underlying infrastructure failures (e.g., a database connection pool exhaustion) can trigger thousands of downstream HTTP 500 errors, flooding communication channels and blinding on-call engineers to true root causes.

2. **Prolonged Mean Time to Acknowledge (MTTA) and Mean Time to Resolve (MTTR)**: 
   Human-driven incident triage is inherently manual. On-call engineers must locate raw stack traces, decode cryptic log messages, context-switch between monitoring dashboards, assess system impact, and coordinate across disparate messaging apps.

3. **Cross-Channel Communication Friction & SLA Breaches**: 
   Escalations often get lost across fragmented tools (Slack threads, Telegram groups, Email inboxes). Crucial minutes are wasted trying to notify on-call personnel, leading to unmonitored Service Level Agreement (SLA) breaches during off-hours or critical downtime windows.

4. **Inconsistent Post-Mortem Documentation & Loss of Institutional Knowledge**: 
   Once an incident is resolved under high stress, postmortem creation is frequently delayed or skipped entirely. Root-cause analyses, timelines, and remediation steps are lost in ephemeral chat histories instead of being recorded in version-controlled repositories.

### 2️⃣ Objectives

The primary goal of **Sentinel** is to build an autonomous, multi-agent AI Incident Commander that continuously ingests system alerts, reasons over technical impact, orchestrates multi-channel communications, enforces SLA escalations, and auto-documents postmortems. 

Specifically, the system addresses the problem via the following core objectives:

* **Automate Real-Time Incident Triage & Contextual Reasoning**: Utilize Large Language Models to evaluate raw stack traces, error messages, and payload metadata, instantly classifying incident severity (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`).
* **Dynamic Error Signature Clustering & Override**: Implement a sliding-window temporal aggregation engine (e.g., 20–30 minute windows) that detects error signatures ($N \ge 3$ recurrences) and automatically forces a 1-level severity escalation (e.g., `HIGH` $\rightarrow$ `CRITICAL`).
* **Unified Multi-Channel Communication via Caspian SDK**: Create a single, normalized message routing hub that translates alerts and thread interactions seamlessly across Slack, Telegram, and Email.
* **Natural Language Intent Parsing for On-Call Interaction**: Parse conversational engineer replies (e.g., *"ack 8b3fb055"*, *"looking into payment DB overflow"*, *"resolved"*) without requiring strict slash commands or UI navigation.
* **Automated SLA Escalation Engine**: Execute asynchronous background polling loops (30-second ticks) to monitor unacknowledged incidents and dynamically escalate across notification channels (Slack $\rightarrow$ Telegram $\rightarrow$ Email $\rightarrow$ Voice) if SLAs are breached.
* **Autonomous GitHub Postmortem Publishing**: Synthesize entire incident life cycles into structured Markdown postmortems (Summary, Root Cause, Timeline, TTR, Prevention Actions) and commit them automatically to a target GitHub repository upon incident resolution.

### 3️⃣ Existing Methodology / Approach

Current industry approaches to incident management rely on static, rule-based heuristics and manual human intervention:

| Aspect | Traditional Approach (PagerDuty, Opsgenie) | Proposed Approach (**Sentinel**) |
| :--- | :--- | :--- |
| **Severity Assessment** | Static pre-configured rules based on static HTTP status codes or log levels. | **Dynamic LLM Triage** evaluating stack traces, technical impact, and historical context. |
| **Deduplication** | Basic grouping by static tags or exact string matching; often fails on subtle log variations. | **Sliding-Window Error Clustering** with automated severity level escalation overrides. |
| **User Interaction** | Rigid UI clicks, specialized mobile apps, or exact slash-commands (`/ack`). | **Natural Language Intent Parsing** across Slack, Telegram, and Email. |
| **Escalation Path** | Time-based phone/SMS alerts; channel switching is manual and disconnected. | **Integrated Multi-Channel Engine** with automated SLA tracking and unified context. |
| **Postmortem Workflow** | Manual document creation in Confluence/Notion hours or days after resolution. | **Autonomous Postmortem Synthesis** committed directly to GitHub on resolution. |

### 4️⃣ Input Data – Detailed Information & Size

Sentinel processes two distinct streams of data: **System Telemetry Data** (unstructured/semi-structured) and **Human Conversational Data** (unstructured text).

#### A. Data Characteristics & Schemas
1. **Inbound Webhook Telemetry**:
   * **Sources**: Sentry, Datadog, Prometheus, Custom Webhook Endpoints.
   * **Attributes**: `source`, `error_signature` (hash/MD5 of normalized stack trace), `raw_payload` (JSON payload containing error stack, host, environment, timestamp), `service_name`.
   * **Payload Size**: $2\text{ KB} - 50\text{ KB}$ per raw alert payload.
2. **Human Conversational Inputs**:
   * **Sources**: Slack thread replies, Telegram group messages, Email responses.
   * **Attributes**: `sender_id`, `channel_type`, `message_text`, `timestamp`, `thread_id`.
   * **Payload Size**: $< 1\text{ KB}$ per text message.

#### B. Data Volume & Temporal Windowing
* **Throughput**: Scalable to handle streaming alert bursts of $1,000 - 100,000$ events/day.
* **Sliding Context Window**: Evaluates recent historical context over a sliding 20–30 minute window containing up to 100 related events per cluster for prompt context injection.

### 5️⃣ Proposed Model Architecture

Sentinel employs a **Multi-Agent System Architecture** powered by a Large Language Model reasoning core, decoupled backend services, and a unified multi-channel communication hub.

```
                      ┌─────────────────────────────────────────┐
                      │    Inbound Telemetry / Webhook Stream   │
                      │    (Sentry / Datadog / Custom APM)      │
                      └────────────────────┬────────────────────┘
                                           │
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │    FastAPI Webhook Processing Engine    │
                      └────────────────────┬────────────────────┘
                                           │
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │       Severity Reasoning Agent          │
                      │  - Google Gemini 2.5 / Flash Core       │
                      │  - Sliding-Window Signature Clustering  │
                      │  - Automated 1-Level Severity Override  │
                      └────────────────────┬────────────────────┘
                                           │
                                           ▼
                      ┌─────────────────────────────────────────┐
                      │   Async Database Storage (SQLite/PG)    │
                      │   Incidents | Events | Thread Context   │
                      └─────────────┬───────────────────────────┘
                                    │
           ┌────────────────────────┴────────────────────────┐
           │                                                 │
           ▼                                                 ▼
┌───────────────────────────┐                   ┌───────────────────────────┐
│ APScheduler Engine        │                   │ Caspian CommClient Hub    │
│ - 30-Second SLA Ticks     │                   │ - Unified @on_message     │
│ - Channel Escalations     │                   │ - Slack, Telegram, Email  │

┌───────────────────────────┐                   ┌───────────────────────────┐

└───────────────────────────┘                   └────────────┬──────────────┘

                                                             ▼
                                                ┌───────────────────────────┐
                                                │ Auto Postmortem Agent     │
                                                │ - Markdown Synthesis      │
                                                │ - Automated GitHub Commit │
                                                └───────────────────────────┘
```

#### A. AI Agentic Pipeline Breakdown
1. **Severity Reasoning Agent (`app/agents/severity_agent.py`)**:
   * Evaluates technical impact of raw stack traces.
   * Checks database for related events within the last 30 minutes sharing the same `error_signature`.
   * **Clustering Override Logic**: If signature count $N \ge 3$, forces an explicit severity level bump and logs `"CLUSTERING OVERRIDE TRIGGERED"` into the immutable reasoning log.

2. **Natural Reply Intent Parsing Agent (`app/agents/intent_parser.py`)**:
   * Inspects incoming chat replies across channels.
   * Maps natural language into structured actions: `ACKNOWLEDGE`, `RESOLVE`, or `CLARIFICATION_REQUIRED`.
   * Supports short-ID resolution (e.g., matching `ack 8b3fb055` to UUID `8b3fb055-xxxx-xxxx-xxxx-xxxxxxxxxxxx`).

3. **Auto Postmortem Agent (`app/agents/postmortem_agent.py`)**:
   * Triggered upon incident status transition to `RESOLVED`.
   * Aggregates event history, severity reasoning, human response timelines, and resolution notes.
   * Generates a GitHub-flavored Markdown postmortem and automatically commits it via GitHub REST API.

#### B. Infrastructure & Tech Stack
* **Language & Framework**: Python 3.11+, FastAPI (Async REST Server).
* **Database & ORM**: SQLite (`aiosqlite` driver) / PostgreSQL with SQLAlchemy 2.0 Async ORM.
* **Background Scheduler**: APScheduler (30-second polling ticks for SLA enforcement).
* **Communication SDK**: Caspian CommClient for unified cross-platform messaging (Slack API, Telegram Bot API, Resend Email API).
* **User Dashboard**: React 18, Vite, Tailwind CSS (Instrument-panel theme with synthetic `/demo/chaos` incident generator).

### 6️⃣ Approximate Number of Model Parameters

The architecture leverages a hybrid model execution paradigm:

```
Total Active Parameters = Core Reasoning LLM (~8B - 12B) + Embedding/Utility Models (~110M - 335M)
```

1. **Primary Reasoning LLM (Google Gemini 2.5 / Flash)**:
   * **Parameters**: **~8 Billion to 12 Billion active parameters** (Mixture-of-Experts architecture optimized for high-throughput, low-latency reasoning).
   * **Role**: Zero-shot severity reasoning, JSON extraction, conversational intent parsing, and postmortem generation.
   * **Latency**: $< 800\text{ ms}$ average response time per completion call.

2. **Embedding Models (Optional for RAG Knowledge Base Integration)**:
   * **Parameters**: **~110 Million – 335 Million parameters** (e.g., `text-embedding-004` or `bge-small-en-v1.5`).
   * **Role**: Semantic similarity searching across internal runbooks and historical postmortems.

3. **Fine-Tuning Capability (On-Premise Privacy Deployment)**:
   * Designed for drop-in substitution with open-weight models (**LLaMA-3 8B Instruct** or **Mistral-7B Instruct**) running locally via vLLM or Ollama for data-sensitive enterprise environments.
